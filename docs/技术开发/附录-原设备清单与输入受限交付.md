# 原设备清单与输入受限交付实施细则

R019接通已领取原租约的执行清单和原始输入受限交付，当前37/95显式控制操作、65表/664列/113外键。INT-094/095先登记权威契约与固定编号；两个GET仅接受原签名设备，不隐式领取。每次读取沿同一原订单优先锁序复核原买方key/路由/同单资金/资格、完整已占预算、原设备版本、输入、物理owner/双围栏和原期限。独立交付服务无签发私钥，输入必须通过原AES-GCM/AAD、独立版本化HMAC和同档位Preflight，按原始字节返回。客户端用独立公钥、原订单/路由/模式及本机内核批准核验清单和租约，有界接收输入；不自动批准内核或提交模型。此为PLAINTEXT/STANDARD可信平台经认证连接交付，密文摘要不能当原文明文签名，不是E2E或卖方不可见。领取/读取均不ACK、不续期、不重派、不完成DELIVER任务、不计费/清锁。001—010及端侧DDL原字节保持；真实宿主持久命令、tokenizer/内核/usage/渠道、E2E/LP/PE/租赁和完整验收仍待。

## 使用顺序与模块

1. 平台原生输入/首签发服务保存原订单、完整预算、加密原文、原首租约和清单。SDK生产监听与Relay Grant还未接线。
2. 原设备持久保存claim命令后，`PrepareLeaseClaim → Send`领取原lease；库不冒称已实现宿主持久队列。
3. 同一个预配置Client执行`PrepareManifest(leaseID) → Send`。从独立原订单/路由/本机批准记录读取Approval和公钥，调用`AcceptDelivery`。
4. 只有成功后才`PrepareInput(leaseID) → Send → AcceptedDelivery.AcceptInput`，返回短寿命内存buffer；消费方负责清零。收到输入不是实际模型执行。
5. 后续须由真实宿主将已核验记录接至受本地共用门闩保护的适配器；监督器当前Work仍是元数据，没有通过本轮偷偷加入prompt/argv或真实GPU调用。

| 模块 | 代码 | 责任 |
| --- | --- | --- |
| 元数据类型 | dev/src/client/protocol/executionlease/manifest.go | 原清单/Spec保持原JSON字段顺序与hash，不生成本机批准 |

## 配置字段

`P11_LEASE_VERIFIERS_FILE`保持原`P11_LEASE_VERIFIERS_1`公钥格式，支持仅元数据领取/读取。额外设置`P11_INPUT_DELIVERY_KEYS_FILE`才开放原输入，其JSON严格只有：

```json
{
  "profile_id": "P11_INPUT_DELIVERY_KEYS_1",
  "fingerprint_version": "fp_original",
  "fingerprint_keys": {"fp_original": "<原32字节指纹钥的无填充base64url>"},
  "input_keys": {"input_original": "<不同目的的原32字节内容存储钥的无填充base64url>"}
}
```

上限16384字节；必须有显式`P11_PAYMENT_ENVIRONMENT`且与Claims相同。文件存忽略runtime并由宿主保护；不能写入README/日志/截图/Git。库复制owned key并在Close清除，宿主也必须关闭返回的清理函数；不承诺系统级秘密生命周期或内存反调试。仅持公钥的manifest服务不依赖解密文件。重试GET仍每次重新检查权限、原期限并使用新nonce，不隐式续租。

验证入口：`python -B -X utf8 dev/tools/原生数据库验证.py --round R019 --suite delivery`为明确的有限回归；完整回归去掉suite。结构、原生源码、真实浏览器/当前二进制和真实设备/渠道门槛分别记录，不混为完成。最终结果见[本轮验证报告](../../dev/tests/evidence/R019-验证报告.md)和[全部待办](../../dev/progress/R019-本轮实现与完整待办.md)。
