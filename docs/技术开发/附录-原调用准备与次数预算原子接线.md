# 原调用准备与次数预算原子接线

R016 / `ROUTE_PREPARE_1`。承接 RC-001—022 与 OBC-001—017，推进 DEV-03、09、11、12、17、25、51、53。当前实现范围是三个原生文本协议的原调用准备库；不新增公开模型入口，不签发执行权。React/Taro 小程序优先、React/Vite Web、NB04 新粗野主义和具体设备型号要求继续适用；部署、HTTPS、运维和可观测性继续延后。

## 一次准备的处理逻辑

1. 受信协议 preflight 应先验证方言、精确字段、公开模型与输出上限，计算瞬时精确正文摘要，保存原请求键；原生 SDK 请求正文保持 OpenAI/Anthropic 规范。本轮没有挂载这个入口。
2. `invocation.New` 明确加载配置，`Prepare` 开启 READ COMMITTED 事务。`PrepareTx` 只用于需要同事务组合的内部服务；调用方负责提交，禁止在事务内进行网络、引擎或渠道 I/O。
3. `LockForPreparationTx` 重新检查当前 key/用户/角色，从 key 绑定路由中精确匹配模型与方言。多个候选包含失效候选，一律拒绝歧义。取得原订单写锁后加载固定合同及当前资格/资金/容量。
4. 查询同买家/路由/原键的已提交任务。存在则核对原 API key 和原 HMAC 版本，返回同一 job 的当前状态、原 deadline、reservation 状态及当前剩余额度；不再占次数或预算，也不重写安全事件。
5. 不存在则要求当前路由 ACTIVE；校验最大 token 成本被单次上限覆盖，冻结最短截止，先生成最终 job ID 与 reservation ID。
6. 插入 INPUT_PENDING；调用 `budget.ReserveIdentifiedTx` 按最终预算 ID 预留完整单次额度；追加仅四字段的安全事件。延迟外键与约束在提交时验证互相引用，任意缺失整体失败。
7. 确认提交后才把元数据回执交给调用方。提交结果未知时只查询/重放原键原参数；内部事务不自动重试，不能先启动后端再补元记录。

`Prepare` 返回 `JobID/OrderID/RouteID/SellerID/State/Deadline/ReservationID/BudgetState/ReservedFen/RemainingFen/UsedCalls/Replayed`。这些不是 `relay.Grant`、ExecutionLease 或资金证明。`ReservedFen` 表示原最大预留额，当前状态另见 BudgetState，不把历史最大值当作当前消耗。

## 数据与指纹

| 存储位置 | 字段 | 内容与限制 |
| --- | --- | --- |
| p11.jobs | invocation_profile | ROUTE_PREPARE_1 或历史 UNBOUND_JOB |
| p11.jobs | route_contract_id / invoker_key_id | 固定原路由及创建该原调用的 key |
| p11.jobs | caller_key / request_digest | 原意图键域隔离摘要 / 版本化 HMAC；均不保存原正文 |
| p11.jobs | fingerprint_version | 恢复时选原 HMAC 钥，不能覆盖成最新版 |
| p11.jobs | invocation_spec | 精确四项 protocol_profile_id、public_model、max_output_tokens、stream |
| p11.jobs | reservation_id | 原预算外键，延迟到 COMMIT 校验，唯一关联 |
| p11.budget_reservations | purpose_ref / purpose_kind | 原 job ID / JOB，ORDER_CAPACITY_1，RESERVED，整笔单次上限 |
| p11.outbox_events | safe_payload | 只有 job/route/order/contract_hash，不含请求摘要和秘密 |

HMAC 输入是固定结构序列化的 `P11_INVOCATION_FINGERPRINT_1 + Buyer + Route + Key + BodyDigest + Spec`；所有实现端应调用同一库而非自行拼接替代算法。`RequestDigest` 为严格 64 位小写十六进制。它仍依赖上游可信 preflight，不能接受未经验证的客户端自报摘要作为正文一致性证明。HMAC 只降低持久摘要的离线猜测风险；平台明文网关和本机推理仍须另按既有隐私文档处理。

原正文摘要按精确字节计算，包括空白和键顺序；语义相同但重新序列化的不同字节仍属于不同输入，同原键提交会冲突。入口应冻结原请求，不能在未知提交后重新拼装参数。标准 SDK 的公开请求格式不变，幂等头/可信程序原键的实际映射和兼容矩阵尚待入口实现与验证。

Close 使用互斥锁清除库复制的密钥；调用方仍负责其原输入副本。缺旧版本应恢复秘密配置或进入人工恢复，不能重建 job。当前实现没有生产秘密文件加载、KMS、轮换调度或删除策略，不把库接口当作已交付完整密钥生命周期。

## 冲突、恢复与并发

| 场景 | 处理 | 资金/次数 |
| --- | --- | --- |
| 同原键、同参数、同 key 并发 | 一条新准备，其余原号恢复 | 一条预算、一份次数、一条事件 |
| 同原键改任一绑定参数/key | CONFLICT | 保留原记录，不创建替代调用 |
| 不同原键竞争最后一次/最后额度 | 原订单写锁后只允许合法数量提交 | 未获准者无任务、预算、事件 |
| key/角色/用户当前撤销或越界 | 当前鉴权失败，新请求及原重放都拒绝 | 原记录继续保留 |
| 原路由/设备/资金已失效但身份仍有效 | 仅可恢复既有记录 | 原 hold 与次数不清零 |
| 旧 HMAC 钥缺失或服务关闭 | UNAVAILABLE | 不重新准备或执行 |
| 事务回滚、缺预算/缺事件、延迟 FK 不满足 | 整笔失败 | 不允许只占次数/只留任务 |
| 后续取消/过期/未知 | 保留原意图，继续查询原任务和可信资格 | 不按猜测释放或消耗 |

本轮 `MaxCalls` 对“已接受准备意图”计数。后续产品若需要取消后返还次数，必须单独设计有编号、不可变、可核对的额度返还事实及用户规则，不修改原调用或把计数改成成功条数。007唯一约束使每个原订单当前只确认一份路由；该路由各次调用与原订单其他合法预算用途共用同一剩余额度，不能复制出另一份可花余额。

## 后续执行准入

当前这一阶段只完成“准备调用 → 原订单额度”。后续 DEV-17/18/25 应完成输入授权和可用性、原任务上下文、当前资格、可信资金、原预算、同物理资源 owner 与双围栏的统一事务校验，再签发 ISSUED 租约/受限原调用 Grant。只有此后才能从受信 secret_ref 取后端凭据并提交一次；未知提交查原 backend key，停止清理证据决定资源何时可复用。

E2E 将独立落实 PREPARED recipient/attempt/token/context 与买方封装确认，平台不得看到内容；不能将本轮明文正文摘要逻辑套入密文正文并声称已经实现 E2E。显卡租赁仍需父会话、按小时计时、硬截止和清理验收。usage/成交资格/支付渠道必须由可信生产器接入，不能用本轮合成 SETTLED/资格夹具开售。
