# 原退款持久事务与宿主恢复源码

本附录为 R026 / CODE_FIRST 的 RT-001—040，承接 RF 原生退款协议及 CK/GF/PT/PH 原付款链。当前补入原退款服务、独立当前审批、未消费价款检查、原实付回执重新 RSA 验签、前向 018 及原生宿主恢复接线。代码、SQL 和测试定义均未编译或运行；不构成真实个人卖家退款资格、真实清理、资金结算或完整交付的证据。全 56 任务/222 子项继续开放，生产源码、实际依赖接线和测试源码完成后再统一验证。

## 1. 当前实现与完整业务范围

新增 `RefundService` 依赖同一个 `Machine`、同一数据库、已有独立 Proof/财务归档 keyring，以及明确登记的原退款渠道。创建服务不会运行迁移、审批、网络请求或后台循环。`Host.Refunds()` 仅在原生受信任配置显式给出退款注册时返回服务；普通 Machine Pay 注册不会自动增加退款能力。

本次实现 `UNUSED_BALANCE_1`：独立金融审核人批准原交易未消费价款退款。它是完整售后体系中的一个明确分支。含费合同的退款分摊、已赚取服务价款冲销、佣金/分账回退、已付续租退款、卖家到账/结算对账与自动取消/售后决策，仍须各自完成真实渠道适配与账务接线，不能用本分支替代。本档仍继承原显式零费用收款产品范围，不修改其他含费产品的合同或价格。

当前只有服务和原生宿主/专用 worker 源码接线；公开退款 HTTP、审批工作台和双端售后页面还未接入。原计划 `createRefund` 的“买家申请→售后审核”合同保持原用途，不能直接替换成买方自批退款。新增服务输入只是引用既有独立批准，不接受买家指定退款金额、去向、自由文本原因或费用接收人。

## 2. 注册与独立批准

`RefundRegistration` 包含 refund route ref、原 capability ref 和独立 `AlipayRefund`。它必须与 Machine 内保留的原 app/卖家/service/环境/双公钥 pin 完全一致，route 的证据引用和摘要也必须对应原收款产品保存的退款能力证据。重复 ref 或重复原 capability/route 组合拒绝安装；已关闭的 Machine 不能新装服务。

新建退款及首次提交均重新校验当前独立审批。原两项收款/个人卖家资格继续采用金融恢复校验；原退款能力证据还需覆盖原 scope、退款 profile、route revision/hash 和两个精确方法。售后决策类型为 `MACHINE_PAY_REFUND_DECISION_1`，要求当前 ACTIVE 的 PAYMENT_REVIEWER/self，且审核人独立于买卖双方，角色未撤销/过期，证据为当前 APPROVED。

| 审批范围 | 固定内容 |
|---|---|
| 原收款身份 | profile、seller/app/service/environment、revision、authority subject、双公钥 pin |
| 原供给合同 | SKU、mode、privacy、collection、order/payment/buyer、contract hash |
| 原退款能力 | refund profile、route revision/hash、两个原生方法 |
| 原金融决策 | UNUSED_BALANCE_1、原实付 evidence hash、批准时 order/payment version |
| 原金额 | 以规范十进制整数分字符串记录本次金额及累计最高可退金额 |

服务从独立证据读取金额，而不是从买方输入读取；冻结必要字段的安全快照与摘要。`decision_evidence_id` 在退款上下文中全局唯一，同一审批即使换幂等键也只返回原退款。新的部分退款必须有新的独立决策并重新占用累计额度。

提交后查询不重新审批一笔退款，也不依赖新销售 gate；仍须原注册、原金融恢复窗口、当前原授权和精确退款路线有效。售后决策撤销阻止尚未提交的退款；已提交的不确定金融义务继续按原号查清，不从额度中删除。

## 3. 价款、执行与累计锁

所有生产写路径先锁原订单，再锁原付款及其 Machine 上下文，最后读取/锁退款及任务。资金消费者仍使用 GF 的“单独父订单锁语句→READ COMMITTED 新快照”检查，避免等待锁期间插入退款的幻读。

创建和首次提交都检查：原付款 SETTLED、原 ORDER 与合同金额对应；无未结束 job、未清理的已签发 attempt、活动执行租约、未 CLOSED 的租赁、仍由原任务/租赁持有的资源锁；无保留/未核实预算或旧式预算记录。已消费额必须与已解决预算及追加成交资格金额一致。未停止或未清理不能通过到期、超时或钱包回调被解释成“没有消费”。

本次退款及所有既有 REQUESTED/PROCESSING/UNKNOWN/SUCCEEDED 的累计占用不得超过原未消费实收。服务没有权威失败档位，既有 FAILED 记录需要独立复核，不直接视作可再次使用的金额。前向 018 还约束原退款义务与订单预算之和，防止后续预算写入重新消耗已占退款价款。

批准和记录仍不能证明现实世界中的设备已经停工；实际物理清理证据和故障组合留待全量代码后的真实验证。

## 4. 原实付重新验签

创建退款读取原 VERIFIED_PAID 回执，核对原 scope、交易号、原摘要和归档密文摘要；用财务 Vault 解密完整原 envelope 后，再通过 `Alipay.ReverifyPaidReceipt` 在保留的原支付宝公钥 pin 下重新验证原始响应节点的 RSA2 签名。它同时检查 code、active、原 trade_no/out_trade_no、精确金额和原金融元数据，拒绝重复 JSON、改签名、跨单/跨金额或超期。

这一操作只读本地已保存回执，不发出新的付款、Proof 或渠道查询。首次退款提交再次核验冻结的那份原回执；后续正常的原付款查询即使产生新的已付回执，也不要求把已批准退款替换成新意图。归档 AES 解密与重新 RSA 验签为两步，任何一步失败都不能放行退款。

## 5. 同事务创建和原号恢复

| 阶段 | 同事务持久内容 | 外部动作 |
|---|---|---|
| 买方引用独立批准 | 原累计预留、不可变 scope/intent/route/decision、原实付回执引用、REFUND/QUERY 意图、专用 job、outbox、安全幂等结果 | 无 |
| 首次后台认领 | 原付款跨退款 3 秒水位、UNKNOWN、原 dispatched_at、generation、REFUND=SENT、20 秒工作租约 | 提交恰好一次原退款 |
| 后续认领 | 至少 10 秒边界、同一原退款号、推进 generation、QUERY=SENT、独立任务认领 | 查询同一原退款 |
| 正常结果写回 | 完整签名回执密文、原退款状态、channel safe_result、outbox、当前任务处理 | 无新退款 |
| 迟到原成功 | 原签名事实及 SUCCEEDED 同事务记录 | 不能确认别人的新认领代次 |
| 资格/执行/预算未决、期限到达或认领上限 | 原金额继续占用，任务 DEAD、review_required、原事件 | 不清成失败/余额、不另建原号 |

后台使用 `RESOLVE_MACHINE_REFUND` 专用任务，只选择本宿主安装的 route refs；每轮最多认领一个原退款。认领租约为 20 秒，generation 不回绕，最多 128 次认领（含首次提交），此后保留义务进入独立复核。3 秒延后不计一次外部调用；每次查询准备把下一次最早查询时间再推进 10 秒。

崩溃发生在“UNKNOWN 已提交，但实际请求可能未发出”时，恢复也只能查询原号。不能因为查询尚未收到、code=10000、缺失状态、网络异常或局部超时而自动再提交退款。权威失败后的同号重试和人工恢复属于后续独立策略，当前不通过改状态或换号实现。

`fund_change=Y` 及累计 `refund_fee` 继续按 RF 规则保持 PROCESSING；只有精确原号、原金额/实收、已验签且明确 REFUND_SUCCESS 的查询才形成成功事实。收到响应后的保存使用独立 5 秒上下文，调用者取消不会直接丢弃已核实的迟到金融事实。过期工作进程可以追加原签名回执并记录真实成功，但只有自己的 job generation 和 snapshot generation 都仍匹配时才更新当前任务及共享查询结果。

## 7. 原生宿主和关闭顺序

原生 host 配置可显式增加 `original_refund_routes` 数组，每项包含 `refund_route_ref`、`original_capability_ref` 和完整的 `route`。原 capability 必须已存在于同一原注册表；签名、公钥和可选授权 token 均从该注册的原受信任根相对文件读取，不接受网络地址、任意路径或买家上传密钥。route 仍需真实独立审批，配置本身不审批。

`RunRecovery` 为付款恢复、退款恢复、资金准入和 Proof 退役依次提供处理机会；某一类渠道失败不跳过其他类。构造不启动循环，只有原专用 worker 入口显式运行它。关闭时先取消并等待实际循环返回，再关闭 RefundService、Machine、独立退款渠道、付款渠道及最后的两组 Vault。超时仍保留所有者，不伪造 join 或清理成功。

API 宿主目前可以持有该条件服务，但公开售后 handler 尚未配置。支付 worker 可处理来自已批准上层服务的持久退款任务；当前尚无公开功能默认创建这类任务，未配置 route 的宿主不认领、不代选原卖家退款能力。
