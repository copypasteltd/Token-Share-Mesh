# 订单预算预留与资格化消耗实施细则

P11｜R014｜2026-10-30｜DEV-02/10/12/38/39/53。源码为`dev/src/internal/budget`，权威前向迁移为[006](database/migrations/006_order_budget_capacity.sql)。本附录承接[交易合同](附录-NB价版与交易服务实施约束.md)、[支付账务](13-支付退款账务与渠道结算.md)及[固定路由转发](附录-固定路由协议转发核心实施细则.md)。

## 1. 预算的含义与调用边界

本轮实现订单内部的容量账：原订单上限＝新格式预留＋已资格化消耗＋旧格式未核实占用＋剩余容量。全部为整数分，既有小时/M token有理费率及累计取整规则不变。剩余容量不是渠道确认资金、可提现余额、跨卖家钱包、预授权冻结或付款成功证明，也不赋予路由、租约、显卡执行或资源释放权限。

`ReserveTx`、`CompleteTx`、`LookupTx`、`SnapshotTx`只执行调用方提供的PostgreSQL事务；不自行提交、不进行外部I/O、不启动内核。未来生产准入必须先验证当前身份/scope、原RouteContract、卖家/设备资格和资金事实，并将预算预留与持久调用/任务意图写在同一事务，再沿原执行授权进入引擎。当前`p11-api`/`p11-node`没有因此增加模型监听或预算HTTP入口，仍31/93控制操作、65平台表。完整生产准入、真实验付和资格生产器仍待接入。

Scope只由可信应用依据原订单/路由事实构造，绑定原order/buyer/seller/contract_hash。库校验其与数据库一致，但不把知道这些字段当作用户认证。不能直接解码客户模型JSON或复制未验证Lease来生成Scope。普通标准SDK正文不增加私有预算字段。

## 2. 数据与锁序

006为orders新增budget_reserved_fen、budget_consumed_fen、budget_unverified_fen三列；为budget_reservations新增accounting_profile、purpose_kind、consumed_fen、qualification_id、resolved_at五列。新profile为ORDER_CAPACITY_1，原amount_fen保存预留上限，consumed_fen只保存最终资格化实际额。未有资格时保持NULL，不写零。

库调用遵守订单→原purpose预留→资格的锁序；直接SQL仍受守恒约束，但不承诺避免死锁，失败必须整笔回滚，不能在事务里执行外部调用。新预留和最终完成均真实UPDATE父订单的容量计数，不依赖旧快照中的SUM再插入；Read Committed下串行分配，Repeatable Read旧父行快照发生序列化失败。库没有自动重试事务或外部执行；调用方处理已知回滚与提交未知时，必须沿原purpose查询。

数据库触发器同时检查上限、用途、终态与来源。直接普通SQL也不能删除预留、调整已预留金额、重开终态、伪造零释放或直接清父计数。父计数只由嵌套预算触发器改变；数据库owner/DDL权限分离仍遵循原物理模型说明，本轮不声称可对抗关闭触发器的数据库管理员。

## 4. 完成与恢复流程

新调用在完整准入事务中固定原purpose，按已确认规格的最坏费用预留；成功提交后才允许后续执行。相同purpose的任何重放读取原预留/终态，不形成第二次执行许可。客户端没有稳定调用键时，相同正文仍可能表示两个独立意图；预算primitive不代替网关调用幂等。

已验证的计费/接受模块先产生追加不可变的trade_qualification，预算完成事务再核来源与原用途，读取实际额并一次完成。来源生产器仍须验证真实用量、最终性、价版、接受/租赁区间；本库不能从一条合成资格推导真实事实，也不会创建资格。取消未证实或真实费用不明时继续保留全部预留，待可信核实后处理；不能为改善可用额度假造零费用资格。

Complete允许在原订单过期/关闭后处理其原先已发生的合法结果；Lookup与Snapshot同样允许历史读取。Reserve到期后拒绝，包括原purpose重放；恢复方应调用Lookup查询原结果。资格失败不部分改变计数，已资格化费用超预留则保留原预留并交由差异处理，不追扣或扩大旧合同。

零费用释放与正费用差额返回只改变订单内部容量，不发送渠道退款、结算或佣金冲正。租赁最终计量沿原session，不创建第二个按量订单或额外收款；旧租赁表的分钟字段仍只适用精确兼容案例，任意小时价租赁迁移和完整续租仍待完成。
