# 退款申请、独立审核与双端售后源码

本附录是 R026 / CODE_FIRST 的 RA-001—040，承接 RT 的原退款事务和 RF 的原渠道适配。新增源码尚未编译、测试或运行，019 未迁移。当前补齐原订单售后申请、独立审核、原退款意图的原子组合、七个控制接口、React/Taro 与 React/Vite 售后面板及 Web 金融审核工作台。全部 56 任务、222 子项继续开放，完整生产源码、实际依赖和测试源码完成后统一验证。

## 1. 三种状态与原合同

买家申请不是独立批准，也不是渠道退款。原 `createRefund` 保留“申请原单合同内退款”的用途，不能改成买家携带任意审核结果后自批。申请没有收款账号、退到新卖家、任意渠道地址、原始 prompt、结果内容或自由文本字段；原金融动作仍绑定原付款、原卖家、原合同与原退款号。

| 审核状态 | 渠道状态 | 含义 |
|---|---|---|
| PENDING | REQUESTED | 售后申请已保存；没有创建金融退款或调用渠道 |
| REJECTED | REQUESTED | 申请未批准；没有渠道退款，不能显示成渠道 FAILED |
| APPROVED | REQUESTED/UNKNOWN/PROCESSING/SUCCEEDED | 独立批准已和原退款意图同事务保存；金融状态仍取原退款记录 |
| REVOKED | 原金融状态保持 | 审批已撤销；尚未提交的原意图不能放行，已提交或未知义务继续原号核对 |

`confirmed_fen` 只有原渠道已验签的精确查询确认 SUCCEEDED 才等于申请金额，其他情况为 0。原退款号贯穿申请和金融记录，批准后不换一个公开申请号。审核 `review_version` 和金融 version 各自推进；公开 version 为两者的单调组合，不用审批版本覆盖金融进展。

当前可执行策略仍为 `UNUSED_BALANCE_1`、原显式零费用档，单笔 1—5000 分。含费合同分摊、已赚取服务价款冲销、佣金回退、续租退款、卖家到账与结算对账全部仍是完整需求，不能用本分支替代，也不能声称已完成退款体系。

## 2. 买家申请与双方查询

申请输入为 `expected_order_version`、有限 `reason_code`、`requested_fen` 和最多 50 个 `evidence_refs`。原因限不再需要、服务无法继续、核对剩余价款三种安全代码。引用必须确属原买家和原订单，只保存引用，不自动开放证据内容；完整选择性举证授权仍由后续争议体系实现。

服务先验证当前账户和 BUYER，再锁原订单、原 ORDER/SETTLED 付款和原 Machine 上下文，检查订单版本和申请额。每单最多一项 PENDING：相同内容换键仍返回原申请，改内容不能覆盖。原请求字节和摘要、双方身份、合同、金额、引用、事件、安全审计及幂等结果同事务保存；不创建金融预留、不调用渠道、不释放执行或预算。

原买家和原卖家可分页查看该单申请与原金融状态；买家不能读取其他订单，卖家不能代买家申请。分页每页 1—50 项，使用不含秘密的最后原记录 ID；游标只是过滤条件，不能授予跨单权限。API key、设备凭据和过期账户不能代替本人会话。

## 3. 当前独立审核与原子批准

审核工作台使用当前会话与 `refund:review`，每次查询、写入及幂等重放都重新验证 `PAYMENT_REVIEWER/self` 当前授权。审核人须独立于买卖双方。新角色范围仅由既有真实角色产生，不给普通登录默认授予审核资格，不提供自助提权入口。

审核详情包含原买卖双方、当前订单/付款/审核版本、已实收额、已占退款额、未消费累计上限、安全证据引用，以及当前安装并通过原路线审批的 route refs；不包含完整签名回包、付款凭据、客户生成内容或客户密钥。显示的余额摘要不能替代批准时的当前资格及清理复核。

批准必须显式选择原登记路线、核对三种当前版本和批准累计上限；后台独立生成 `MACHINE_PAY_REFUND_DECISION_1`，冻结原 scope、申请摘要、审核人、金额、当前原实付摘要和版本。完整批准事务依次完成当前路线/审批校验、原 RSA 回执重验、活动执行/清理/预算守恒检查、原累计退款预留、原 REFUND/QUERY 意图、专用工作任务、事件及申请 APPROVED。任一步失败全部回滚，不留下孤立批准或没有退款的决策证据。

审核服务使用审核人的真实主体，不伪造一个买家 Principal。公共审批路径与 RT 的原决策消费路径共用同一个 `createApprovedRefundTx`，保留原生退款全部金融门槛；HTTP 宿主必须持有同一个 Machine 的 RefundService，不能拼接另一数据库或付款注册。

拒绝只更新售后审核与安全审计，不写渠道 FAILED，不创建金融退款，也不释放其他原退款。并发审批使用原父锁、原申请锁、当前版本和幂等约束，最多产生一个原金融意图。

## 4. 撤销批准与恢复

当前独立审核人可按原审核版本撤销 APPROVED，同时将那份不可变决策标记 REVOKED；原 scope、摘要、审核人和证据有效期不能借撤销改写。尚未提交的工作任务在提交前再次检查独立决策，撤销后停入独立复核并保留金额。已有 UNKNOWN/PROCESSING/SUCCEEDED 不被撤销倒退、删除或解锁。提交后的查询沿用 RT 原号恢复规则。

客户端遇到网络失败、5xx、无法核验的成功响应时保存原账号/路径/安全正文/幂等键，只能显式恢复同一操作；不同参数不能替换未知请求。401/403/429 不销毁原记录。会话或订单变化使晚到响应失效，不能覆盖另一账号的界面或删除原账号未决记录。损坏记录保留并阻止新写，不静默重建。没有保存 prompt、生成结果、付款凭据、完整回执或 token。

Taro 订单详情和 React/Vite 订单详情复用同一 `RefundFlow`，提供申请原因/金额、审核状态、金融状态、已确认退回金额、原操作恢复和分页刷新。卖家页面展示原订单申请，不显示买方提交按钮。Web 账号页面仅为持有审核权限的用户展示独立工作台；批准前显式核对原路线、累计上限和审核确认。使用既有 NB04 新粗野主义组件与小时/M token 的服务单位，不新增按媒体结果收费。
