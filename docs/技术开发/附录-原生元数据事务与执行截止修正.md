# 原生元数据事务与执行截止修正

P11｜R013｜2026-10-30｜DEV-18/20/21/24/53。承接[执行元数据库](附录-原生执行收件箱与资源门闩实施细则.md)与[原生执行监督](附录-原生执行监督与后端恢复实施细则.md)。本轮修改真实原生Go/SQLite控制代码；后端仍是合成元数据适配器，不运行模型或真实显卡。

## 已复现的问题与修正

初次五项受控负向回归全部失败，原始事件在`dev/tests/evidence/R013-deadlines-before-fix.jsonl`。包括：SQL开始前的取消毒化健康账证、排队者无法及时取消、事务耗时在返回后重新成为可用租期、实际适配器context截止晚于签名expiry，以及多步骤共用耗尽的数据库预算。一次原生后端探针实测发现4.2828毫秒的截止延长；这个值只描述该次回归，不是性能指标或所有历史失败的统一根因。

| 编号 | 约束 | 实现与边界 |
| --- | --- | --- |
| NMD-001 | 元数据串行门闩支持取消 | Store使用有界单令牌门闩；排队期间可以返回，不要求等原事务结束，不创建额外工作线程 |
| NMD-002 | SQL开始前取消不破坏健康账证 | 获门闩后再次检查context；未触碰SQL即返回ErrStorage，不设置poisoned，不释放、重置或替换owner |
| NMD-003 | SQL或提交不确定仍关闭 | BeginTx后SQL/提交错误继续毒化该Store并关闭新准入；不能把任何超时都当作健康取消或自动重试 |
| NMD-004 | 原生截止锚在元数据工作之前 | 每次事务在Clock.Sample前记录带单调分量的time.Now；Receive/Renew依原签名剩余量建立固定原生deadline |
| NMD-005 | 三项时间限制取最早 | 原签名绝对时间、端侧Elapsed与固定原生deadline共同限制执行；后续Current/Activities不重建原生期限，合法新签名Renew另行处理 |
| NMD-006 | 事务返回不得带过期执行权 | Activity附带固定Deadline；提交后重算Remaining，耗尽则Authorized=false；原资源仍占用，须实际停算与清理 |
| NMD-007 | 后端调用不能从返回时重新计时 | Submit取Activity.Deadline、CallTimeout、运行上下文中最早截止；副作用前再次检查调用方取消，不用相对Remaining重启一段租期 |
| NMD-008 | 各数据库步骤独立预算 | Receive、Current、BeginSubmit、映射、停止、查询结果持久化、清理分别取得新MetadataTimeout；不继承已耗尽的前一步预算 |
| NMD-009 | 数据库和适配器预算分离 | MetadataTimeout默认2秒，20毫秒—5秒；CallTimeout默认1秒，20毫秒—5秒。前者只控制元数据I/O，不延长后端调用或签名租期 |
| NMD-010 | 退出绝对截止保持 | 元数据context忽略普通取消以保存安全状态，但继承当前监督/退出的更早绝对截止；停止未确认仍ErrShutdown并保留占用 |
| NMD-011 | 减少重复持久写 | 已知相同backend不重复写映射；已失权快照不反复写STOPPING；同一恢复流程不重复写已进入的停止阶段 |
| NMD-012 | 清理证明不减少 | 依然核对原请求、backend、完整owner代次和WorkStopped/TokensRevoked/WorkspaceCleared/hash；普通ACK、到期、断线均不能FREE |
| NMD-013 | 清理完成唤醒退出 | FinishCleanup成功且slot释放后，单元素内部通知唤醒退出循环重读；普通查询/失败重试不通知、不形成忙循环，不扩大ShutdownTimeout |

额外的确定性回归复现：原500毫秒退出预算结束时，SQLite已为FREE，旧循环却因等待下一次1秒轮询误报ErrShutdown。修正只增加持久清理完成后的有界内部唤醒；主循环仍重新查询账证和busy状态后判断，通知本身不作为停算/清理证明。首轮139项回归当时为138通过、1个慢I/O退出失败，已保留原记录。

## 调用与配置

可信宿主仍按显式初始化→NewSupervisor→RunSupervised→等待Ready→Submit使用原库。Options新增MetadataTimeout；未配置时取2秒。原CLI没有因此新增推理入口、平台钥安装、后台自启动或GPU资格，execution_enabled仍为false，设备心跳仍报告UNKNOWN。

调用方取消发生在SQL之前时，原健康库仍可用新context查询/停止/清理；监督器收到ErrStorage仍锁闭新准入并取消在途调用，不自动恢复新任务。实际SQL错误的旧Store继续不可用，须按既有显式重开与原owner恢复规则处理，不能删除库或换目录绕过。

设置较短ShutdownTimeout时，各元数据步骤受该总截止压缩；预算耗尽允许保守失败，不能为了退出成功宣称已停算或放松owner比较。普通Go context不能抢占忽略context的恶意适配器，也不能提供操作系统硬实时或强制GPU停止证明。
