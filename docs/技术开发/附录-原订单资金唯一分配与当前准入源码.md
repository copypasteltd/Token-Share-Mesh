## 2. 资金、预算和执行的关系

`order_fundings` 记录“这笔原付款被分配给这个原订单”。它既不划转货币，也不创建可提现余额、授信或通用余额；没有任何钱包操作。原验签金融事实和原 receipt 永久保留，当前资格则在每次使用时重新判断。

一个原订单可多次读取同一份资金资格，仍须分别通过原订单的预算预留、当前主体/目录、资源 owner/双围栏、输入/模式、硬截止和执行许可检查。该分配不等于单次调用实际消费，不替代可信 usage、小时水位、用户接受或账务。原小时租赁继续使用 RENTAL_SESSION，不生成普通 T1/job/attempt，不按图/视频产物数量收费。

当前唯一可写的付款产品为显式注册 `SELLER_DIRECT_NO_FEE`：原合同 commission_bps=0、buyer_fee_fen=0，个人卖家价格符合原总预算。完整费用、佣金、渠道退款/到账/对账仍保留需求，不能为了迁就旧测试合同而把原费率静默改成零。

## 3. 恢复事务

1. 原 `RecoverOne` 通过已批准渠道适配器验证同一原 Proof，保存完整原签名 envelope 的独立钥环密文。receipt/payment/channel/outbox 和唯一元任务同时提交；订单仍保持 WAITING_PAYMENT。
2. `RecoverFundingOne` 只从本宿主注册 capability 的到期元任务发现原付款。事务内重新锁原订单，再锁原付款/context，最后锁专用任务；已 DONE/DEAD 或未到期的任务不重做。
3. 在第一次写入前复核原合同摘要、原金额/用途/环境/注册、当前双方及个人卖家、四项审批和原 gate、当前目录、零费用档位、硬截止和零预算占用。出现业务拒绝只更新安全任务状态；原 SETTLED 不回退。
4. 用原 receipt 构建不可变分配；同事务将原订单从 WAITING_PAYMENT 推进 READY、增加版本、保存 `OriginalOrderFundsAdmitted` 安全 outbox 和任务 DONE。只含 order/payment/funding/receipt ID，不含 Proof/session、PEM、token、原生回包或正文。
5. 提交结果不明确时，重新读同一原任务和唯一分配。已有同付款分配则确认元任务，不新增资金/事件，不重新调用金融渠道。旧 READY/FULFILLING 无分配不倒补，关闭/超期原单进入元任务人工处理状态。此处没有自动退款接口。

## 4. 退款并发与当前读取

资金消费者必须使用 READ COMMITTED，并保留原父行锁。`CurrentTx` 故意先用独立语句取得原订单 SHARE，再用下一语句读取原分配、付款、receipt 和退款集合。若原退款写入方尚未提交，第一次语句等待原订单；等待结束后的第二个语句获得新快照，能够看到已经提交的退款。把所有条件塞进一个 JOIN/锁语句不能证明没有退款幻行。

017 的原 Machine refund 触发器同样锁原父订单，覆盖直接 SQL 插入。正式退款应用服务仍必须先锁原订单、原付款，再接触退款行，避免从子行反向等待父行造成锁序循环。当前触发器保护串行和原记录，不能认证一个退款渠道回包；完整退款状态机仍在 GF-034。

当前检查还锁定原分配、原付款/context/receipt、双方及角色、个人卖家资料、四项 evidence/reviewer/角色和原 gate。每次重新核验有效性，返回期限收窄到最早当前审批/角色期限，末尾再读取数据库时间确认尚未过期。普通数据库记录读锁不等于未来永久授权；执行/控制路径仍必须持续按自己的原约束检查。

## 5. 三个消费者

| 消费者 | 接线 | 拒绝行为 |
|---|---|---|
| `routecontract.Service.original` | 绑定原 order/payment 和显式服务环境；CurrentTx 后再核原合同、当前目录和预算等既有规则 | 当前资金冲突使原路由不可用，历史仍可查；原数据库错误继续上报，不伪装为已付款 |
| `rental.Service.fundingTx` | 绑定原订单和可选原付款；Funding.Evidence 使用唯一分配 ID，原小时条款不变 | 无分配/退款/撤权/超期拒绝更多授权，不自动放 owner 或原预算 |
| `identity.KeyService.Create` | 从准确原路由/付款读环境，不能让调用者选默认环境；新 key 不超过路由和当前资金期限 | 当前资金不合格时不生成新 secret；旧 key 调用仍经路由当前准入重核 |

没有对 `SYNTHETIC_TEST`、测试环境、空 profile 或任意后台地址的生产例外。旧正向测试中直接写 READY/SETTLED 的源夹具尚未升级，必须在完整代码阶段替换为资格化源链；不跳过原用例、不降低断言、不为通过测试改原商业合同。GF 的新正向定义使用原 native SQL + 注册的合成 RSA2 付款链，仍然不是真实支付宝、真机或实际资金验收。
