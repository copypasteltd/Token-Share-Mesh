# 原订单付款挑战与双端恢复源码

当前为 R026 / CODE_FIRST，CK-001—040。源码、接口、页面和测试定义均未编译或运行，全部56项任务、222个子项仍开放。本文承接原MP/PT/PH/GF支付与资金准入，不替换原合同、账务或统一API。先写完整生产代码、实际依赖接线和测试源码，之后集中测试调试；本次是源码保存点。

## 1. 需求与当前源码边界

买方需核对本单个人卖家、原合同金额，选择当前获准的原卖家收款能力；创建结果未知时查原订单的原付款，复用原请求键恢复。收到钱包回调后只提交原凭据，原生专用worker核验，后续独立资金准入再检查当前资格。付款、资金分配、READY、设备准备、计量和执行各自保存真实状态。

本次补入五个正式本人控制接口及两个端的订单页和共享状态机。没有安装获准的真实PayLauncher，两个实际前端的付款唤起按钮保持关闭；接口和状态机不是普通SDK的付款前授权。当前SDK路由与API key仍要求真实资金就绪，不能为方便付款而取消这些门槛。

本次不改SQL；已登记平台001—017双份迁移和全部端侧DDL/source.json保留原字节。将来需要新结构时只新增前向018+。当前收单能力仍限显式SELLER_DIRECT_NO_FEE原零费用合同，原有含佣金/买方费用合同不可暗改为零费。

## 2. 固定接口编号与约束

所有路径位于`/v1/p11`；使用当前用户会话、原BUYER角色、当前主体版本与原买方所有权。GET没有请求体/查询参数。WEB写操作沿用Cookie、精确Origin、会话CSRF；原生小程序使用内存Bearer。普通模型API key不能代替本人会话。

| 编号 | 操作与路径 | 输入与成功响应 | 实际行为 |
|---|---|---|---|
| INT-099 | GET `/orders/{order_id}/payment-options` | 原订单；200 PaymentOptions | 当前四证/gate/市场条件和原合同；最多8个同环境原卖家能力；不创建付款/不选择 |
| INT-100 | GET `/orders/{order_id}/payment` | 原订单；200 Payment | 读取原唯一ORDER Machine付款；没有则404；不等于允许换键再买 |
| INT-101 | GET `/payments/{payment_id}/challenge` | 原付款；402 MachinePayChallenge + amtPaymentLink | 仅当前可售原PENDING付款，同一已提交预付参考号；不再调用precreate |
| INT-102 | POST `/payments/{payment_id}/proofs` | 严格`{}`、Idempotency-Key、恰好一个Payment-Proof头；202 MachineProofRecovery | 同事务原凭据密文/QUERY/专用job/安全重放响应；不inline verify/READY |
| INT-103 | GET `/payments/{payment_id}/proof-recovery` | 原付款；200 MachineProofRecovery | 最新原恢复元数据；没有则404；不解密、不再查询渠道 |

新增四个schema为PaymentOption、PaymentOptions、MachineProofRecovery、MachinePayChallenge。当前共103规划操作、124 schema、75平台表、55个正式控制HTTP源码路由。固定编号只追加，不重排原INT/DATA。

PaymentOptions只包含原订单、卖家、合同摘要、原版本、人民币分金额、环境和公开付款能力引用/商品名。不能泄露app私钥、代调用token、内容钥、批准原件、完整注册scope或秘密引用。原付款DTO只含安全状态与原渠道参考；页面状态去掉预付参考号，独立内存挑战容器只在明确操作中使用。

## 3. 原402与官方付款链

官方依据：[Machine Pay指南](https://aipay.alipay.com/docs/ai-receive/MACHINE_PAY.html)、[precreate API](https://aipay.alipay.com/docs/ai-receive/api-list/alipay-aipay-agent-payment-precreate.html)、[verify API](https://aipay.alipay.com/docs/ai-receive/api-list/alipay-aipay-agent-payment-verify.html)。本次阅读的是2026年11月6日可见页面，不构成平台实际服务/个人卖家获得收单资格的证明。

官方链路使用precreate返回的`amt_pre_pay_id`构造`amtPaymentLink`，客户端完成付款后产生Base64 JSON `Payment-Proof`，原服务端按同一原凭据verify。本站402只用于本人原付款控制接口；它包含原付款号、精确元字符串、CNY和原截止时间。未知付款不会产生新挑战，402读取也不会创建另一笔渠道请求。

`amtPaymentLink`不是跳转URL，也不是普通支付宝小程序`my.tradePay`的`trade_no`。目前尚未有本项目获准且已接入的客户端能力可以完整返回Machine Proof，因此不拼造链接、app_id、桥接调用、付款证明或“付款成功”回调。PayLauncher是实际适配的窄接口约定，生产入口未配置具体实现，不用模拟桥充当已实现能力。

## 4. 双端原付款操作顺序

1. 打开本人订单，解析本单原合同，绑定原买方/卖家/订单/合同摘要/金额/版本；历史合同保持原样。
2. GET原付款。已有付款只读取和恢复同一原号；没有时才读取当前选项。损坏或不匹配的本机恢复记录保留并阻断，不删除后另建。
3. 用户明确选择能力后，先用安全随机数生成原createKey/proofKey并持久化安全元数据，再POST原意图。失去响应时沿用原参数/原键；UNKNOWN只查原付款。
4. 原PENDING、原本机journal齐全、未发起过、获准PayLauncher明确支持原环境时，用户才可发起。先GET同一原402，核对原付款/金额；发起前持久保存launchRequested，再调用真实端能力。
5. 端能力返回PaymentProof时，经内存对象单次提交到原付款专属头。返回null、取消或异常都不能推定未付款；保存原发起事实并查询，禁止自动再次唤起或换号。
6. 202只展示“凭据已提交”。GET原恢复/原付款，以服务端核验事实展示PENDING/UNKNOWN/VERIFIED/SETTLED；不会调用任务、密钥、资金分配或租赁接口。订单刷新和付款刷新分别执行。

小程序使用React/Taro，Web使用React/Vite，共享`PaymentFlow`。沿用04新粗野主义组件类和原订单价款表达，M token仍区分输入/输出，租赁按小时，不引入按结果收费。面板不展示Prompt、生成结果、私有收款材料或内容钥。

## 5. 内存、持久化与会话隔离

| 对象 | 保存位置 | 生命周期与约束 |
|---|---|---|
| 原订单/卖家/摘要/金额/版本、能力引用、原createKey/proofKey、原付款号、launchRequested | 原账号/原订单命名空间的本地安全元数据journal | 输入约束、精确字段集合、有界4096字符；不保存客户内容或金融秘密；网络前先保存 |
| WEB会话 | HttpOnly Cookie，CSRF在当前内存会话 | 不加入付款journal，切换/失效清理当前投影 |
| 小程序Bearer | 当前进程会话内存 | 不写付款恢复journal；换账号或新会话废弃旧异步结果 |
| 原预付参考号 | PaymentChallenge内存对象 | 普通JSON/字符串序列化脱敏；单次取用/截止检查/结束关闭，不放UI状态/存储 |
| Payment-Proof/client_session | PaymentProof内存对象和一次原专属HTTP头 | 普通JSON/字符串序列化脱敏，单次消费，finally关闭；平台按既有AES-GCM原范围保存短期恢复 |
| 服务端原恢复状态 | 原数据库安全DTO | 仅id/payment/state/expires，无秘密回显；渠道worker独立恢复 |

删除JavaScript引用不能保证字符串、原生桥、浏览器内部或操作系统内存被物理清零。代码避免主动持久化和展示，但不作无法兑现的彻底擦除承诺。客户端和服务端均不得把HTTP头对象、完整钱包回调或异常内容直接记录到日志。

每次换订单、版本、合同、会话或登出递增epoch并关闭内存对象。相同买方的新会话也使旧请求失效。旧请求完成、旧Proof回调、旧null回调和旧finally都不能写入新界面/清除新对象。离开面板只取消本地当前投影，不撤销已提交付款、删journal或声称退款。

原付款从另一客户端创建而本机没有原journal时，只能读取；不能凭空生成恢复键再次唤起。跨端继续付款、原钱包查询/丢失回调恢复仍需实际获准端能力和具体协议实现，作为未收口需求保留。

## 6. 服务端锁序与独立业务事实

本人读取和操作都在同一个正式DB内核验身份/角色/原所有权；原订单先锁，再载入原付款/上下文，保持既有支付与退款父锁顺序。已撤销新售资格仍允许合法主体读取原财务义务，原凭据金融核验沿用既有金融恢复所需批准；不会用“还能查账”重新开放销售。

Proof头只允许精确的POST原proofs路径，大小与Base64 JSON形状限制、重复/混合大小写头拒绝；请求结束和解析后移除请求头中的引用。CORS只对精确路径允许Payment-Proof，其他接口拒绝。严格JSON空对象、原幂等键、当前买方权限均独立检查。Proof不允许放在URL、查询、请求体或标准模型请求私有字段。

核验worker不会由该202立即执行。实付归档、SETTLED单调事实、独立ADMIT_MACHINE_FUNDS、当前四证/退款/截止重查、DATA075唯一分配、原READY/outbox和之后的原设备/租赁/预算条件沿用GF，不由前端回调替代。
