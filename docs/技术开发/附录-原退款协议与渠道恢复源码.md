# 原退款协议与渠道恢复源码

本附录为 R026 / CODE_FIRST 的 RF-001—040 源码约束，承接 MP/PT/PH/GF/CK，不改变 C2C 主体、原合同、费用、资金资格和统一 API。当前只补原退款域模型、独立原生渠道适配、调度前状态转换和签名回执加密归档；平台退款事务、独立资格决策、worker/host/HTTP 实际接线尚未补齐。源码和新增测试定义均未编译或运行，全部 56 项任务、222 个子项继续开放；先完整生产源码、实际依赖接线和测试源码，再集中验证。

## 1. 官方依据与独立资格边界

于 2026-11-06 阅读的支付宝官方[统一收单退款接口](https://aipay.alipay.com/docs/subscribe/api-list/other-basic-interfaces/alipay-trade-refund.html)描述 `alipay.trade.refund`、原交易和原退款请求号、退款金额及同交易提交间隔。官方[退款查询接口](https://aipay.alipay.com/docs/subscribe/api-list/other-basic-interfaces/alipay-trade-fastpay-refund-query.html)描述 `alipay.trade.fastpay.refund.query`、原退款号和明确成功状态。[Machine Pay 指南](https://aipay.alipay.com/docs/ai-receive/MACHINE_PAY.html)是原收款协议的依据；通用收单接口的存在不能证明 Machine Pay 交易、当前个人卖家或本平台第三方代调用已获得退款权限。

因此默认 `P11_MACHINE_PAY_PREPAID_1` 的方法仍只有 precreate 和 verify，不追加虚构的 agent refund 方法。新增 `P11_ALIPAY_ORIGINAL_REFUND_1` 是独立且默认未注册的条件适配档：它必须绑定原支付 `Binding.Digest()`、独立 route revision、真实批准证据引用及摘要、有效期和原财务查询期限。当前配置对象只表达注册要求，不能替代数据库中当前有效、可撤销且与原卖家/app/service/环境/双公钥 pin 一致的独立审批。

`refund-profile.json` 明确实际资格、平台事务和 host/worker/HTTP 退款接线均为 false；不存在可公开触发本适配器的默认退款入口。原四证中的 `MACHINE_PAY_REFUND_ROUTE_1` 也必须证明适用于本单的真实能力，不能由这个新 JSON 或管理员填入任意摘要来替代。

## 2. 原退款不可变范围与金额

`RefundScope` 绑定原付款的 payment/order/buyer/seller/purpose/purpose_ref/contract hash/binding hash/out_trade_no，再绑定本次 refund_id、原 out_request_no、route hash、独立售后决策引用及摘要。`RefundIntent` 另冻结原渠道 trade_no、原实付证据摘要、本次金额、原实收金额、独立决策最高额度、创建时间、最晚提交时间和财务恢复截止。

`NewRefundIntent` 只接受 SETTLED 原付款和 REQUESTED 原累计退款预留；原卖家、绑定、决策及金额必须一致，创建时间不得早于原验付事实。此构造器不自行验证数据库审批或重新验证旧签名，调用者仍须先验原实付签名与独立决策，再在原订单→原付款→退款的锁序内预留累计额度并持久化不可变意图。

本档遵循原 Machine Pay 1—5000 分范围，使用整数分和精确十进制元转换，不使用浮点、指数、四舍五入或溢出截断。通用返回金额允许省略末尾小数零，但不能改变值；只有累计退款字段允许零。其他大额、费用、佣金、分账或支付产品须独立档位及真实资格，不能暗改原含费合同为零费用。

同一原退款恢复保持原号、原金额和原决策；新的部分退款须另行取得决策和累计额度。成功、提交中、结果未知均占用原实收额度。当前通用适配器不产生权威 FAILED；丢字段、业务错误、超时或查询暂未成功都不能释放额度。显式失败后的原号重试仍是待实现的独立策略，不能由自动恢复推断。

## 3. 原生协议与签名

新增 `AlipayRefund` 独立拥有从原 `AlipayConfig` 复制的应用私钥、支付宝公钥、第三方 token 和取消/关闭生命周期；沿用原 app、卖家授权、环境及双公钥摘要校验。真实网络仅使用固定支付宝对应环境入口、RSA2 请求签名、原始响应节点验签、8 秒上限、64 KiB 响应上限、重复 JSON 拒绝及禁止跳转的传输。

| 动作 | 原生方法 | 仅发送的业务字段 | 结果的用途 |
|---|---|---|---|
| 原退款提交 | `alipay.trade.refund` | trade_no、out_trade_no、out_request_no、refund_amount | 一次原提交；签名成功响应仍待原号查询确认 |
| 原退款查询 | `alipay.trade.fastpay.refund.query` | 原 trade_no、out_trade_no、out_request_no | 核对原号、本次金额、原实收与明确成功状态 |

本适配器不发送任意退款去向、自由文本原因、模型 prompt、资产内容、费用收款人或分账指令。第三方 token 仍需独立真实授权，不从卖家输入或默认环境推断。私有 `refundOnly` 方法围栏使独立退款适配器只能调用这两个方法；默认收款适配器仍不能调用退款。

官方退款返回的 `refund_fee` 表示原交易累计成功退款额，并非本次部分退款额；即使 `fund_change=Y`，单凭它也不能归属本次原退款。因此源码把签名提交结果保持为 PROCESSING；累计额不得超过原实收，有资金变化时也不得小于本次金额。该保守策略依据[退款响应字段](https://aipay.alipay.com/docs/subscribe/api-list/other-basic-interfaces/alipay-trade-refund.html)，不把累计值写成本次成功额。

查询必须完整且精确返回原 trade_no/out_trade_no/out_request_no、对应本次 refund_amount、原 total_amount；只有已验签且 `refund_status=REFUND_SUCCESS` 才产生私有 `RefundObservation` 成功事实。`code=10000`、缺失状态或其他状态均不足以认定本次退款成功或确定失败。这一判据依据[退款查询说明](https://aipay.alipay.com/docs/subscribe/api-list/other-basic-interfaces/alipay-trade-fastpay-refund-query.html)。缺少归属字段不从请求补写事实，保持 UNKNOWN；不存在跨订单、跨卖家或新退款号恢复。

## 4. 提交前记录、查询节奏与状态保持

| 状态/动作 | 域转换源码 | 将来必须实现的持久事务约束 |
|---|---|---|
| 初始原预留 | REQUESTED，generation=0 | 独立决策、原累计预留、不可变意图同事务提交 |
| 首次提交准备 | UNKNOWN，记录 dispatched_at，generation+1 | 原订单→原付款锁，读取同付款最近提交水位；先提交再唯一外部调用 |
| 原查询准备 | 维持预留，generation+1、推进 next_query_at | 原号专用 job/有界租约；跨进程原子认领和当前资格复核 |
| 签名提交/尚未确认查询 | PROCESSING | 同事务归档原签名回执、安全状态、outbox 和原 generation ACK |
| 精确成功查询 | SUCCEEDED | 同事务原退款事实、资金阻断/账务、归档、outbox 和任务完成 |
| 网络/签名/字段/业务不确定 | UNKNOWN，继续占用额度 | 查询同一原号；不得新建原号、重收费或自动再次退款 |
| 财务查询期限到达 | 保持原金融事实及预留 | 原异常队列/人工最小披露；不得清成 FAILED 或可用余额 |

同原交易提交至少间隔 3 秒；查询在原提交至少 10 秒后开始，随后每次至少 10 秒。`PrepareRefundSubmit` 要求传入在原付款锁内读到的跨进程最近提交时间，`PrepareRefundQuery` 推进已提交 generation。它们目前是纯域转换源码，原生渠道原语不自行保存水位，不能宣称已经实现持久防重或跨进程限流。generation 不得越过有符号 64 位范围，也不能回绕。

源码不允许对已有 UNKNOWN/PROCESSING 再准备提交；重启只能在原财务窗口查询同一原号。签名成功后的迟到不确定结果不能倒退 SUCCEEDED；关闭回执只撤销原文的访问，不撤销已成立的金融事实。原执行截止、提交截止和财务恢复期限分开：停止新销售后可在原财务窗口继续查询，已验签事实可迟到记录，但不重新赋予任务执行、预算、GPU、续租或清锁权限。

## 5. 完整签名回执加密与所有权

`SealRefundReceipt` 使用财务归档 Vault 的 AES-256-GCM 保存完整原响应 envelope，包括原始签名、空白、可选渠道字段和渠道买方字段；普通返回、日志、outbox/job safe_result 不携带原文。AAD 绑定独立归档 profile、key id、原 scope、原 intent 摘要、独立决策、方法/观察种类、本次金额、累计额、证据摘要和观察时间。

归档 keyring 继续与短期付款 Proof keyring 分离；密文只含 key id，不含 key。轮换只有明确保留的原 key 能读旧回执；错钥、改 scope/金额/方法/时间、改 nonce/ciphertext 或把提交回执改标成功都会失败。观察副本共享回执所有权，Close 擦除其持有的原始字节并禁止通过副本再归档；不声称擦除操作系统、进程转储或数据库 WAL 的所有副本。

`OpenRefundReceipt` 只认证归档并返回受信任读取者拥有的原始字节，调用者必须清理；它不构造 `RefundObservation`，不等于重新 RSA 验签，更不授予退款、付款或执行权限。将来若要用归档重新证明金融事实，必须在原注册/公钥 pin 下重新验签并完整核对原交易与原退款，不能仅凭 AES 解密认定成功。

复用的原生 RPC 生命周期会取消在途请求并等待真正的响应读取/关闭返回；传输忽略取消时仍保有原所有者，不把关闭超时当作实际 join。新增测试源码覆盖这一退款包装路径，尚未执行。
