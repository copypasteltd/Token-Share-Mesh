## 1. 范围和权威

商业关系保持 C2C，提供方仍自主出租自己的闲置设备。媒体调用依附原 RENTAL_SESSION，绑定原买方、卖方、订单、设备、资源、物理身份、逻辑代次、合同、环境和清单，不产生普通 T1/job/attempt，不按生成结果收一次费用。GPU 使用小时计费；文本仍分别记录输入、输出 M token。本附录的容量预留是本机存储保护，不是钱包扣款、可信小时水位或资金释放。

本次实现仅承接已存在的 STANDARD 本机私有执行路径。AES-GCM 本地封装、私有管道、Windows Job Object、受保护目录均不能独立获得 E2E／增强隐私／TEE／低权限或性能资格。DEV-32 在缺少实际证明时继续关闭。

平台双份001—015迁移、原客户端 schema.sql、host-schema.sql 和已登记 schema-002-rental.sql／source.json 保持原字节。本次只新增客户端 schema-003-media.sql／source.json。003 的代码注册不代表已经执行迁移；平台仍71张表、98规划操作、48项控制HTTP源码（含9项租赁），本次两张端侧表不计入平台表数。

## 2. 原节点和数据所有权

生产入口为 node.Store.InitMediaWorkspaces／OpenMediaWorkspaces，使用同一节点已经持有的 OS 锁、原根目录、原 execution.Store。没有第二个资源锁、独立媒体数据库、任意磁盘目录参数或自动目录接管。初始化必须由原本机管理流程显式调用，不能在缺失状态时自动执行。

固定目录结构：

```text
原节点根目录/
  execution.db                 # 原SQLite，追加003的两张表
  media-workspaces/
    namespace.anchor          # 32字节随机锚；不是内容密钥
    ws_<32位小写十六进制>/
      ownership.anchor        # 32字节原工作区随机锚
      cipher-<32位十六进制>.bin.reservation
      cipher-<32位十六进制>.bin
```

namespace_id、锚SHA、工作区原归属及容量在创建对应目录、锚文件或输入/输出文件之前提交原账本。namespace.anchor／ownership.anchor 不是加密密钥；日志仅保存其摘要用于识别原目录。提示词、参数、素材明文SHA、私有结果凭据、内容密钥、工作区 journal key 和资产URL都不落入 SQLite。

节点继承原生保护目录与文件权限，锚文件采用 O_EXCL 和文件 Sync，目录同步沿用原节点平台实现。Windows 原目录同步实现不提供额外目录断电持久性证明，本次不能据此声称通过断电恢复验收。初始化被中断或锚缺失时关闭准入，不换根目录、不补造锚、不重建身份。

## 3. 状态、容量与重放

| 对象 | 正常状态顺序 | 异常规则 |
|---|---|---|
| namespace | CREATING → READY | 重开时未完成的 CREATING → QUARANTINED；不能复用旧票据恢复 READY |
| workspace | CREATING → READY → ACTIVE → RETIRED → REMOVING → CLEANED | 未完成的工作区在重开时全部 QUARANTINED；停止、删除或提交不明均保留原身份 |
| invocation | SUBMITTING → EXECUTING → STOPPING → CLEANING → CLEANED | 工作区未 CLEANED 时不能把原子调用置 CLEANED |
| parent rental | 原 PREPARING／ACTIVE／STOPPING／CLEANING | 清子调用不释放父资源；会话最终清理继续使用原条件 |

每个工作区预留130 MiB物理空间预算；所有未清工作区总预留不超过2 GiB。输入素材最多4个、合计64 MiB；输出最多1个、64 MiB。私有执行器的128 MiB明文上限，加上分块GCM、END、锚及预登记开销，由130 MiB预算覆盖。命名空间保留最多4096条工作区历史，达到上限则拒绝新增，不删除旧历史腾出计费/归属证明。

创建、执行 claim 和删除分别使用一次票据。复制票据不产生新权利。原调用重放仅返回 QUERY_ONLY，原目录不存在也不创建替代目录。目录 basename、锚、namespace、会话、资源、本地代次、原grant及摘要、清单、环境、配方、输入密文摘要和预留容量均不可变；SQL触发器同时约束不可逆状态和历史保留。

## 4. 媒体输入与协议边界

MediaPolicy 从独立本机批准中产生，绑定 COMFYUI、原 workflow ID／revision、协议配置、输出PNG／MP4／WAV／GLB种类和最大输出字节。它不能绑定到文本清单。买方不能用输入选择模型文件、图节点、设备、可执行文件或其他环境。

MediaInput 以原 Bearer 和独立加载的 Expected 验证买方、订单、会话、卖方、设备、资源、代次、合同、环境及清单；输入 descriptor 不包含正文/素材明文摘要。参数最多1 MiB、32个标量项，字符串单项最多64 KiB，拒绝重复键、对象、数组、布尔和非有限数。最终可接受的参数名、类型、枚举和数值范围继续由固定签名配方的有限 slots 约束；允许标量不代表新增一个配方参数。

参数和素材使用新随机 AES-256-GCM 密钥进行 RAM 封装。素材每块64 KiB，AAD绑定原输入描述和素材/块索引，输入标识来自 nonce＋密文，不使用明文指纹。封装需要精确素材长度和 EOF，拒绝少读、多读或零进展。资产源必须由此调用拥有且 Close 能中断 Read；取消会主动关闭源并等待 Close 回调实际结束，整体封装受两分钟上限约束。

Take 只解密一次，复制或关闭别名不能重用。适配器以64 KiB以内临时明文块发送素材，原素材SHA只在内存及私有 INVOKE 声明中使用。发送方结束前清理参数、输入密钥、密文缓冲与借用视图，不能仅因取消等待就报告输入已清。

这些类型是 SDK 解析之后的内部标准化表达，不能作为公开新方言。公开请求仍须使用已经规范的 OpenAI／Anthropic 兼容入口。尚未实现的生图/视频/音频/3D公开映射、本人资产授权和响应映射仍保留待办；不得把私有 INVOKE 开成HTTP、虚构 Anthropic 原生视频接口、把媒体塞进 TextDescriptor 或新增随意执行图入口。

## 5. 本机媒体调用顺序

```text
已本人批准的原 ProviderRental + 原资源账本 + 已选完整Comfy环境
  → OpenPreparedComfy：准备阶段加载；不产生INVOKE权
  → 独立原grant / 新鲜ALLOW / Process.Authorize及ACK
  → BindPreparedComfyMedia：核同准备清单、同hold、同节点工作区Owner
  → SealMediaInput：认证原买方输入并本地封装
  → RentalMediaAdapter.Submit
      → 原 BeginRentalInvocation 一次inbox
      → 原工作区容量/身份登记，创建锚和目录
      → 原工作区一次claim + 原授权复核
      → 私有 INVOKE / ASSET_BEGIN / DATA / END
      → 原 ACCEPTED → 实际后端映射落盘
      → RESULT → 密钥交给本机 MediaCustody
      → STOPPED → 同步停算/撤未来启动/清输入等事实
```

媒体适配器拥有该进程唯一帧读取者，一次只持有一个未清子调用。原 backend ID 从原会话、子调用、本地代次生成，供同一后端查询和取消；它不创建计费任务或改变卖方。输入每次写管道继续检查原控制权限。重复、外来、次序错误或不完整回报关闭该进程；缺少 STOPPED 不能因为进程消失而变成 ABSENT。

适配器是原生子调用叶子组件；当前并未把它接成完整媒体会话监督器或公开SDK生产准入。独立控制轮询、媒体会话ready、付费续租、可信小时水位和平台清理回执不能由此接口补造。

## 6. 结果密钥托管与读取

RESULT 仅从原本机进程接收。凭据必须匹配独立原 workspace scope、输出种类、长度和有限 basename；其中密钥由一次 Receipt 消费。MediaCustody／MediaReader／Workspace／Launch 的格式化和JSON表示均遮盖内容，不能把私有帧或错误原文写入状态接口、日志、截图或README。

MediaCustody 只开放一次读取，包含失败时消费；Open、每次 Read 和 Seek 都复核同一原grant、原物理资源和 EXPORT_SELF。不能因为会话后来有新grant就恢复旧结果读取。读取继续使用已经实现的私有分块GCM文件，核header、记录AAD和认证END，单块解密缓存不超过64 KiB。此文件格式不是网络 BINARY_STREAM_1，读取成功不是买方ACK/可信usage。

ReadLease 同时持有 reader 初始化和实际 Close 的生命周期：在初始化回调结束前不能关闭原root；重复Close也要等待第一次Close真正完成。复制句柄共享关闭状态。进程原生finalizer在释放其 done／环境Use之前撤销托管结果、关闭实际读取句柄和密钥，即使调用方没有主动关闭适配器也一样。会话结束后不能继续依赖此 RAM 托管导出；独立结果留存/端侧E2E交付仍待完成。

## 7. 停工、清理和恢复

子调用 joined 同时需要实际工作端 STOPPED 和发送方已结束/清输入；实际进程、管道和API全部退出只允许撤销本地引用，缺少停工证据仍是 UNKNOWN。STOPPED 必须匹配原调用，并同时携带 work_stopped、future_start_revoked、input_keys_cleared；成功还必须有原 RESULT 且输出钥状态一致。任何一个字段、顺序、ID或结果托管不符都不能产生清理事实。

原调用进入 STOPPING，可信原适配器观察 STOPPED 后，原账本才进入 CLEANING。随后关闭结果仓/所有读取句柄和工作区journal key，退役工作区、提交 REMOVING tombstone，再验证原basename、锚、允许的有限文件清单及最终绝对路径，最后只在原 os.Root 内删除原目录。删除和父目录同步之后才能登记 workspace CLEANED，进而登记 invocation CLEANED；原父租赁不因此释放。

不得以 kill 返回、HTTP关闭、取消ACK、PID不存在、释放Go对象或时间到期推断GPU停算。损坏锚、外来文件、路径变化、删除/提交不确定时保留 QUARANTINED 和原占用。没有默认重试、设备兜底、CPU降级、换卖家或新目录重跑。

恢复入口 OpenOriginalCleanup 只接受已经由独立可信物理停工对账推进到 CLEANING 的原子调用，且仅打开原namespace/原目录/有效锚。它只生成清理引用，不恢复任何输入/结果密钥、INVOKE权或读取权；不存在的锚或未识别目录不能接管删除。实际独立停工对账生产、管理UI和完整恢复组合仍待完成。

节点关闭顺序延续原锁：先停原运行引用/实际进程和密钥托管，再等待工作区引用/读取句柄，之后才能关原账本、清节点master并释放 OS 锁。外部等待超时不能提前放掉这些引用。
